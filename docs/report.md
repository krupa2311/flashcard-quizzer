Executive Summary

I built the Flashcard Quizzer, a command-line application that loads flashcards from a JSON file and quizzes the user in sequential, random, or adaptive mode. It validates input, gives green or red feedback, and finishes with a summary of total questions, accuracy, and missed terms. It also offers three extra features: --limit, --export, and --timed.

All code and tests were generated by Claude Code. My role was to write specifications, review every output, and verify it myself. I worked in phases, committed a snapshot before each re-prompt, and fixed problems by rewriting prompts rather than editing code. The result has 142 passing tests and 100% line coverage.

Project Overview
Problem Statement

New team members need a lightweight terminal tool to memorize terms. It must load decks from JSON, offer different quiz modes, and be clean enough to extend.

Solution Approach

A modular Python 3.10 application using only the standard library. Loading, quiz logic, interface, export, and timing live in separate modules. The three quiz modes use the Strategy pattern, selected through a Factory, so new modes can be added without rewriting the app.

Testing Strategy

There are 142 pytest tests covering the loader, factory, modes, scoring, interface, argument parser, exporter, timer, and full-session integration tests. All five test names from the brief exist. Line coverage is 100%. I excluded test files from coverage after noticing they inflated the figure, and ran a mutation check: inverting the re-queue condition made three tests fail, including test_adaptive_mode_behavior. I wrote tests after each phase rather than test-first.

Design Patterns Used
Strategy: QuizMode and its three subclasses are interchangeable algorithms for choosing the next card, so QuizSession and the interface work with any mode.
Factory: get_quiz_mode uses a QUIZ_MODES registry, ignoring case and spaces. The --mode choices come from the same registry.
Code Structure and Organization

utils/file_handler.py loads and validates, quiz_engine.py holds logic, ui.py handles the terminal, main.py parses arguments and returns exit codes, and utils/exporter.py and utils/timer.py hold the extras. The engine has no print or input, and the interface accepts injectable input and output functions, which made everything testable. I narrowed main()'s error handling so unexpected bugs stay visible.

Technical Challenges and Solutions
Challenge 1: Leftover typed characters after a timeout

Problem: Half-typed text stays in the terminal buffer and would join the next answer.
Solution: I specified that the timer discards unread input, then verified it on a real terminal.
AI Involvement: Claude wrote the implementation from my rule.
Lessons Learned: Mocked tests cannot prove behavior that depends on the real environment.

Challenge 2: Trusting coverage

Problem: The first 99% figure counted test files, and coverage alone says nothing about bug detection.
Solution: I added a .coveragerc and the mutation check described above.
AI Involvement: Claude wrote the tests, and I designed the checks.
Lessons Learned: Deliberately breaking code is a fast way to test the tests.

Reflection
What Worked Well

Phase-by-phase prompts with explicit requirements worked best. Snapshot commits made every AI change visible, and independent verification caught all discrepancies. I am proudest of the adaptive mode and the timer's input handling.

What Could Be Improved

I would name edge cases in the first prompt, and tighten the timer's exception handling. The word exit cannot be an answer, and duplicate card fronts confuse --stats.

Future Enhancements

A spaced-repetition mode, saved progress between sessions, and Windows support for the timer.

Conclusion

This project changed how I see AI-assisted development: the AI writes quickly, but the engineer owns correctness. I will keep using specific phase-based prompts, snapshot commits, and independent verification. Reviewing AI output like a colleague's pull request is a habit I will carry into future work.
